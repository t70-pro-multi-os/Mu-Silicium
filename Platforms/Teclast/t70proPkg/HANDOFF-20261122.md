# T70 Pro 인수인계: 2026-11-22 (KST)

이 문서는 검증된 산출물과 남은 연결을 구분한다. 펌웨어 설치, 파티션 변경,
USB 쓰기 또는 부팅 설정 변경을 지시하지 않는다. `WORKLIST.md`는 계속
수정 중인 보드 전체 작업표다. 아래 산출물 경로는 Mac의
`~/.tmp/teclast-t70pro/` 기준이다.

## 가장 먼저 이어갈 부팅 검증

- **일반 ARM64 QEMU:** 최신 `winpe-refresh-20261122/efi-otg-winpe.refresh.20261122/take-to-device/T70Pro-WinPE-ARM64-Drivers.img`
  (SHA-256 `87b54bd2af846a3db091fe3ac8459f444431db3f2fb4e7421712f27968d1fa2d`)
  를 읽기 전용 가상 NVMe에 연결했다. 65초에 Windows 11 설치 창,
  95초에 드라이버 선택 화면을 직접 확인했다.
  화면과 실행 기록: `winpe-nvme-startup-ui-dr6qwxxp/screen-95.ppm`, `run.json`.
  이미지는 시험 전후 동일하다. `install.wim`, `install.esd`, 분할 `install*.swm`은
  없으므로 전체 Windows 설치 매체가 아니다.
- **일반 virtio 대조:** 새 이미지에서 BCD, SDI, WIM 전체 섹터의 성공 응답을
  확인했다. 하지만 이전·최신 이미지 모두 직접 virtio 경로에서는 110초
  동안 설치 화면을 표시하지 않았다. 읽기 완료를 커널 시작으로 세지 않는다.
  근거: `winpe-virtio-file-reads-vgd1sptk/completed-file-reads.json`.
- **T70 보드 모델:** T70 EFI에서 Windows Boot Manager가 BCD를 읽은 기록까지만
  확인했다. 이전 트레이스는 100개 I/O 이벤트에서 끝났으며, `winload`,
  성공한 `ExitBootServices`, 커널, 설치 UI 증거는 없다. 일반 QEMU 성공으로
  이 빈칸을 채우지 않는다. `winpe-bcd-handoff.yoh1y10R/post-bcd-trace-review-20261121.json`.
- 다음 검증에는 BCD 다음의 SDI/WIM 완료, `winload` 진입, 그리고 성공한
  `ExitBootServices` 또는 Windows 실행 표지를 별도로 기록한다. EBS 호출
  시작 알림은 성공 근거가 아니다. 새 RAM 로더는 예약 페이지 타입을
  요청하지만 EFI 블록 장치만 만들므로 NFIT 게시를 가정하지 않는다.

## Linux, EFI 진단, 부팅 도구

- **Linux initramfs 결합 정렬은 소스에서 수정했다.** 이전 후보는 압축 initramfs 길이 117,102,306바이트 다음 위치에 RAW 모듈 CPIO를 바로 붙여 `070701` 헤더가 4바이트 정렬되지 않았다. 현재 `LinuxBoot.c::LoadInitrd`는 두 번째 archive 앞에 필요한 0~3바이트를 채우고 오버플로를 거부한다. 실제 함수 기반 `LinuxBootTest` 26개 시나리오가 ASan/UBSan으로 통과했다. RELEASE ARM64 EFI 앱은 `Build/t70proPkg/RELEASE_CLANGPDB/AARCH64/T70LinuxBoot.efi`에서 빌드됐으며 크기 44,544바이트, SHA-256 `874717f333d678e07e46bc2d4cfafcc8d41f149e3656d88a58df68e43ba90bbe`다. 커널 실행·ExitBootServices 성공·태블릿 부팅을 뜻하지 않는다.
- 위 결합 정렬 외에도 현 후보에서 LTE `59f3b2e`, Wi-Fi `623777b`,
  Bluetooth `d561c68`의 최신 결과물은 아직 미반영이다. 두 CPIO의 끝까지
  읽고 대상 세 경로가 모듈 아카이브로 덮이지 않는 것을 확인했다.
- **BusyBox DHCP 갱신 거부 처리는 사용자 공간에서 보강했다.** Ubuntu
  `1:1.37.0-7ubuntu1` ARM64 바이너리는 갱신 훅의 실패를 무시하고 새 임대를
  채택할 수 있다. 현재 훅은 갱신 옵션 검증에 실패하면 소유 설정을 정리하고
  그 DHCP 서비스의 대기 프로세스에만 `USR1`을 보내 클라이언트를 종료한다.
  정리 실패 시 소유 기록을 보존하고 별도 상태로 남긴다. 합성 BusyBox 동작을
  모사한 `test_connectivity_services.py`가 이 종료·주소/경로 소유권을 검사한다.
  기존 두 네임스페이스 시험은 BusyBox가 훅 실패를 무시하는 원인을 재현한
  결과이며, 현재 서비스 로직의 전체 네트워크 동작 검증은 아니다.

- Linux Wi-Fi 상태 및 LTE 링크 진단 커밋 `ae527cc`, `92f13bb`. 현재 initramfs에
  두 수정이 들어 있고 최신 `T70LinuxBoot.efi`가 이 initramfs 해시를
  포함한다. 이전 WinPE 검증용 빌드의 Linux 앱과 혼용하지 않는다.
- DeviceCheck 단독 ARM64 앱:
  `devicecheck-visual-linked-dejyfmm2/T70DeviceCheck-97a2595e.efi`.
  현재 소스 콘솔 모의 검사에서 80자, 160자와 폭 2~512열을 확인했다.
  스크린샷/로그를 RAM에 보관하고, 수동 대상 선택과 확인 전에는 쓰지 않는
  정책을 유지한다.
- 별도 `t70pro-boot-switch` 저장소: WinPE 오류 검사 `d600695`,
  CPIO 경계 `6cee29e`, 빈 UEFI 경로 `8cf3a94`, 오래된 SD/UFS 빌드
  기록 검사 `9f0533c`, MBR/FAT32 검사 `9f51d47`, virtio 완료
  추적 `c4fae16`. 최신 오프라인 테스트 154개 통과. 이 도구는 실제
  부팅 변수 변경이나 자동 복구를 구현하지 않는다.

## 작업 경계

기존 OrbStack builder 원본 Git만 사용한다. 현재 다른 작업이 수정 중인
EFI·ACPI·드라이버 파일을 통째로 덮거나 스테이징하지 않는다. 공용 빌드
잠금은 우회하지 않는다. 일반 에뮬레이터, T70 보드 모델, 실제 태블릿,
Windows 드라이버의 링크·주입·동작을 각각 별도로 판정한다.
